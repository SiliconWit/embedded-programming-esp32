## BLE Architecture Overview

<InArticleAd />


Bluetooth Low Energy (BLE) is a radio protocol for small amounts of data at very low power. Classic Bluetooth keeps the radio busy all the time, which suits audio and file transfer. BLE switches the radio on only to send one small packet, then off again. A sensor with a few bytes every few seconds has its radio off most of the time, which is why it can run for months on a small battery.

The differences from Classic Bluetooth:

| Feature | Classic Bluetooth | BLE |
|---------|-------------------|-----|
| Power consumption | 30+ mA sustained | Peaks of ~15 mA, average < 1 mA |
| Connection setup | Seconds | Milliseconds |
| Data throughput | Up to 3 Mbps | ~1 Mbps (effective ~200 kbps) |
| Range | ~10 m typical | ~10 m typical (up to 100 m open air) |
| Topology | Point to point | Point to point, broadcast, mesh |
| Use case | Audio, file transfer | Sensors, beacons, control |

The power figures are for chips made only for BLE. The ESP32 is a larger chip: its radio draws about 100 to 130 mA while it receives or transmits, and the processor tens of milliamperes while awake. This lesson's sensor never sleeps, so on a battery it lasts days, not months. Months need the sleep modes of the [power management lesson](/education/embedded-programming-esp32/power-management-deep-sleep/), or a dedicated BLE chip.

Your firmware meets BLE through two parts. GAP answers "how does a phone find this device and connect to it?"; GATT answers "once connected, what data is there and how is it read?". Think of a shop: GAP is the sign over the door, GATT the counter inside, where each item has its place. The library handles the layers below, which carry the packets.

```text
 ┌───────────────────────────────┐
 │  Application (your firmware)  │
 ├───────────────┬───────────────┤
 │  GAP          │  GATT         │
 │  be found,    │  hold data,   │
 │  connect      │  read, notify │
 ├───────────────┴───────────────┤
 │  ATT and L2CAP: carry the     │
 │  GATT data in small packets   │
 ├───────────────────────────────┤
 │  Link layer: 40 channels      │
 ├───────────────────────────────┤
 │  Radio: 2.4 GHz, 1 Mbit/s     │
 └───────────────────────────────┘
```

### GAP: The Advertising and Connection Layer

The Generic Access Profile (GAP) covers how devices find each other and connect. A BLE device takes one of four roles:

1. **Broadcaster**: sends advertising packets and accepts no connection (a beacon).
2. **Observer**: listens for advertising packets and never connects.
3. **Peripheral**: advertises and accepts a connection. This is the role of our ESP32.
4. **Central**: scans for peripherals and starts the connection. This is the role of your phone.

Advertising is the sign over the door. It works in three steps:

1. The peripheral sends a short packet, at most 31 bytes, on three channels kept for advertising (37, 38 and 39). It repeats the packet at an interval that you choose.
2. A scanning central receives the packet. It can read the data in it (passive scanning), or ask once for a second packet with more data, the scan response (active scanning).
3. If the central wants more than these few bytes, it starts a connection.

### GATT: The Data Layer

After the connection, the Generic Attribute Profile (GATT) says how the data is arranged, so that no phone app needs special code for each device. GATT has four levels:

1. **Profile**: a set of services for one use. It is a design pattern, not something sent over the radio.
2. **Service**: a group of related values. Each service has a UUID, a number that identifies it everywhere. The Environmental Sensing Service is UUID `0x181A`.
3. **Characteristic**: one value in a service. Temperature is `0x2A6E` and Humidity is `0x2A6F`.
4. **Descriptor**: a setting that belongs to one characteristic. The one you will use is the Client Characteristic Configuration Descriptor (CCCD, UUID `0x2902`), the switch a client writes to when it wants notifications.

```text
 ┌─────────────────────────────────────┐
 │ Service: Environmental Sensing      │
 │ UUID 0x181A                         │
 │ ┌─────────────────────────────────┐ │
 │ │ Characteristic: Temperature     │ │
 │ │ UUID 0x2A6E, read and notify    │ │
 │ │ ┌─────────────────────────────┐ │ │
 │ │ │ Descriptor: CCCD (0x2902)   │ │ │
 │ │ │ switches notifications on   │ │ │
 │ │ └─────────────────────────────┘ │ │
 │ └─────────────────────────────────┘ │
 │ ┌─────────────────────────────────┐ │
 │ │ Characteristic: Humidity        │ │
 │ │ UUID 0x2A6F, read and notify    │ │
 │ └─────────────────────────────────┘ │
 └─────────────────────────────────────┘
```

The device that holds the data is the GATT server (our ESP32); the one that asks is the client (the phone). Each characteristic has properties that say how a client may use it: read, write, notify or indicate. Ours allow read (the client asks once) and notify (the server sends each new value by itself). The Humidity characteristic has its own CCCD too; the drawing shows one to save space.

## NimBLE Stack on ESP-IDF

<InArticleAd />


A stack is the library that implements all the layers of a protocol. ESP-IDF offers two for Bluetooth: Bluedroid (from Android, for BLE and Classic) and NimBLE (BLE only, from Apache Mynewt). For a project that needs only BLE, use NimBLE: it takes roughly 50% less flash and 40% less RAM than Bluedroid.

### Enabling NimBLE in Your Project

In `menuconfig`, navigate to `Component config` > `Bluetooth` and set the host stack to NimBLE:

```
idf.py menuconfig
```

<Steps>
1. `Component config` > `Bluetooth` > Enable Bluetooth
2. Set `Bluetooth host` to `NimBLE`
3. `Component config` > `Bluetooth` > `NimBLE Options` > Set device name to `ESP32-ENV`
4. Save and exit
</Steps>

The top-level `CMakeLists.txt` is the usual one:

```cmake
cmake_minimum_required(VERSION 3.16)
include($ENV{IDF_PATH}/tools/cmake/project.cmake)
project(ble_env_sensor)
```

And in `main/CMakeLists.txt`, list the required components:

```cmake
idf_component_register(
    SRCS "main.c"
    INCLUDE_DIRS "."
    REQUIRES bt nvs_flash driver esp_timer
)
```

The `bt` component brings in NimBLE once you have selected it in menuconfig. The DHT22 code needs `driver` for the GPIO and `esp_timer` for timing in microseconds.

### NimBLE Programming Model

NimBLE works like the Wi-Fi event loop: you do not wait for the radio. You give NimBLE functions of your own (callbacks), and it calls them when something happens. There are four parts:

1. **Host task**: NimBLE runs in its own FreeRTOS task, started by `nimble_port_freertos_init`. Your callbacks run inside this task.
2. **GAP event callback**: called when a phone connects, disconnects or subscribes.
3. **GATT access callback**: called when a client reads or writes a characteristic.
4. **Sync callback**: called once, when the NimBLE host and the radio controller are ready. This is where you start advertising, because advertising started earlier fails.

## GAP: Advertising Configuration

<InArticleAd />


Advertising tells nearby phones that the ESP32 exists. The packet holds only 31 bytes, and every field costs 2 bytes (length and type) before its data, so choose with care. This project sends three fields:

1. **Flags**: say that the device can be found and that it is BLE only (2 + 1 = 3 bytes).
2. **Complete Local Name**: the name a scanner shows. `ESP32-ENV` has 9 characters, so 2 + 9 = 11 bytes.
3. **Service UUIDs**: tell a scanner which services the device has. One 16-bit UUID takes 2 + 2 = 4 bytes.

That is 18 of the 31 bytes. A longer name can fill the packet, and then the call that sets the fields returns an error.

The code below sets these fields and starts advertising:

```c
#include "host/ble_hs.h"
#include "services/gap/ble_svc_gap.h"

static const char *device_name = "ESP32-ENV";

static void start_advertising(void)
{
    struct ble_gap_adv_params adv_params;
    struct ble_hs_adv_fields fields;
    int rc;

    memset(&fields, 0, sizeof(fields));

    /* Flags: general discoverable + BLE only */
    fields.flags = BLE_HS_ADV_F_DISC_GEN | BLE_HS_ADV_F_BREDR_UNSUP;

    /* Include the complete device name */
    fields.name = (uint8_t *)device_name;
    fields.name_len = strlen(device_name);
    fields.name_is_complete = 1;

    /* Include 16-bit service UUID: Environmental Sensing (0x181A) */
    ble_uuid16_t ess_uuid = BLE_UUID16_INIT(0x181A);
    fields.uuids16 = &ess_uuid;
    fields.num_uuids16 = 1;
    fields.uuids16_is_complete = 1;

    rc = ble_gap_adv_set_fields(&fields);
    if (rc != 0) {
        ESP_LOGE(TAG, "Failed to set adv fields, rc=%d", rc);
        return;
    }

    /* Advertising parameters */
    memset(&adv_params, 0, sizeof(adv_params));
    adv_params.conn_mode = BLE_GAP_CONN_MODE_UND;  /* Undirected connectable */
    adv_params.disc_mode = BLE_GAP_DISC_MODE_GEN;  /* General discoverable */
    adv_params.itvl_min = BLE_GAP_ADV_ITVL_MS(100); /* 100 ms min interval */
    adv_params.itvl_max = BLE_GAP_ADV_ITVL_MS(150); /* 150 ms max interval */

    rc = ble_gap_adv_start(BLE_OWN_ADDR_PUBLIC, NULL, BLE_HS_FOREVER,
                           &adv_params, gap_event_handler, NULL);
    if (rc != 0) {
        ESP_LOGE(TAG, "Failed to start advertising, rc=%d", rc);
    }

    ESP_LOGI(TAG, "Advertising started");
}
```

The advertising interval sets how often the packet is sent. A short interval (100 ms) lets a phone find the device quickly but uses more power; on a battery you might use 1000 ms. Our board runs from USB, so 100 ms costs nothing.

### Connection Mode and Discoverability

The `conn_mode` field determines whether a central can connect:

| Mode | Constant | Behavior |
|------|----------|----------|
| Non-connectable | `BLE_GAP_CONN_MODE_NON` | Broadcast only, no connections |
| Undirected connectable | `BLE_GAP_CONN_MODE_UND` | Any central can connect |
| Directed connectable | `BLE_GAP_CONN_MODE_DIR` | Only a specific central can connect |

Our sensor uses undirected connectable, so that any phone can connect.

## GATT Server: Services and Characteristics

<InArticleAd />


The GATT server holds the data that the device offers. In NimBLE you describe it as a table: you list your services and characteristics in a static array, and NimBLE handles the protocol.

### UUID Types

BLE uses two forms of UUID:

1. **16-bit UUIDs**: given out by the Bluetooth SIG, the body that owns the standard, for standard services and characteristics. Environmental Sensing Service is `0x181A` and Temperature is `0x2A6E`.
2. **128-bit UUIDs**: numbers you make yourself for data that has no standard. Format: `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`.

Temperature and humidity have a standard, so we use the 16-bit UUIDs. A client that knows the Environmental Sensing Service then knows the meaning and the format of our data with no code written for our device.

### Defining the GATT Table

NimBLE defines the GATT structure using an array of `ble_gatt_svc_def` entries. Each service contains an array of characteristics, and each characteristic can have descriptors:

```c
#include "host/ble_uuid.h"
#include "services/gatt/ble_svc_gatt.h"

/* Characteristic value handles (set by NimBLE during registration) */
static uint16_t temp_chr_val_handle;
static uint16_t humi_chr_val_handle;

/* Forward declarations */
static int gatt_access_cb(uint16_t conn_handle, uint16_t attr_handle,
                          struct ble_gatt_access_ctxt *ctxt, void *arg);

/* GATT service definitions */
static const struct ble_gatt_svc_def gatt_svr_svcs[] = {
    {
        /* Environmental Sensing Service (0x181A) */
        .type = BLE_GATT_SVC_TYPE_PRIMARY,
        .uuid = BLE_UUID16_DECLARE(0x181A),
        .characteristics = (struct ble_gatt_chr_def[]) {
            {
                /* Temperature characteristic (0x2A6E) */
                .uuid = BLE_UUID16_DECLARE(0x2A6E),
                .access_cb = gatt_access_cb,
                .val_handle = &temp_chr_val_handle,
                .flags = BLE_GATT_CHR_F_READ | BLE_GATT_CHR_F_NOTIFY,
            },
            {
                /* Humidity characteristic (0x2A6F) */
                .uuid = BLE_UUID16_DECLARE(0x2A6F),
                .access_cb = gatt_access_cb,
                .val_handle = &humi_chr_val_handle,
                .flags = BLE_GATT_CHR_F_READ | BLE_GATT_CHR_F_NOTIFY,
            },
            {
                0, /* Terminator */
            },
        },
    },
    {
        0, /* Terminator */
    },
};
```

A handle is the number NimBLE gives to each entry of the table when it registers the service. NimBLE writes these numbers into the `val_handle` variables, and you use them later to say which value a notification carries. The `flags` field sets the properties: read and notify.

## Characteristic Values and BLE Data Formats

<InArticleAd />


A standard characteristic has a fixed format. BLE sends whole numbers, not fractions, so each standard value is a count of small steps. Send any other format and a phone app shows a wrong value.

### Temperature (0x2A6E)

The Temperature characteristic is a signed 16-bit integer (`int16_t`) that counts steps of 0.01 degrees Celsius. A reading of 23.45 C is sent as `2345`, and -5.30 C as `-530`.

### Humidity (0x2A6F)

The Humidity characteristic is an unsigned 16-bit integer (`uint16_t`) that counts steps of 0.01 percent relative humidity. A reading of 55.20% is sent as `5520`.

### The GATT Access Callback

When a client reads a characteristic, NimBLE calls the access callback. The callback adds the value to the reply, which NimBLE keeps in a buffer of type `os_mbuf`:

```c
/* Current sensor values (updated by the sensor task) */
/* Start at the standard "value is not known" (0x8000 and 0xFFFF), so a
   phone that reads before the first reading sees no false 0.00 C */
static int16_t current_temp_ble = INT16_MIN;  /* Temperature in 0.01 C units */
static uint16_t current_humi_ble = 0xFFFF;    /* Humidity in 0.01% units */

static int gatt_access_cb(uint16_t conn_handle, uint16_t attr_handle,
                          struct ble_gatt_access_ctxt *ctxt, void *arg)
{
    uint16_t uuid16;
    int rc;

    uuid16 = ble_uuid_u16(ctxt->chr->uuid);

    switch (ctxt->op) {
    case BLE_GATT_ACCESS_OP_READ_CHR:
        if (uuid16 == 0x2A6E) {
            /* Temperature: sint16, little-endian */
            rc = os_mbuf_append(ctxt->om, &current_temp_ble,
                                sizeof(current_temp_ble));
            return rc == 0 ? 0 : BLE_ATT_ERR_INSUFFICIENT_RES;
        }
        if (uuid16 == 0x2A6F) {
            /* Humidity: uint16, little-endian */
            rc = os_mbuf_append(ctxt->om, &current_humi_ble,
                                sizeof(current_humi_ble));
            return rc == 0 ? 0 : BLE_ATT_ERR_INSUFFICIENT_RES;
        }
        return BLE_ATT_ERR_UNLIKELY;

    default:
        return BLE_ATT_ERR_UNLIKELY;
    }
}
```

BLE sends the low byte of a number first (little-endian order): `2345` is `0x0929`, and it travels as the bytes `29 09`. The ESP32 stores numbers the same way, so the code copies the variable as it is.

### Converting DHT22 Readings to BLE Format

The DHT22 driver returns temperature as a float in degrees Celsius and humidity as a float in percent. Multiply each by 100 to get the BLE value:

```c
static void convert_sensor_to_ble(float temp_c, float humi_pct)
{
    /* Temperature: multiply by 100 to get 0.01 C resolution.
       Round (math.h): a plain cast cuts off, and 20.3 becomes 2029. */
    current_temp_ble = (int16_t)lroundf(temp_c * 100.0f);

    /* Humidity: multiply by 100 to get 0.01% resolution */
    current_humi_ble = (uint16_t)lroundf(humi_pct * 100.0f);
}
```

A reading of 24.3 C and 61.8% gives `2430` and `6180`. The rounding matters: a float cannot hold 20.3 exactly, `20.3f * 100` is a little below 2030, and a cast that cuts off the fraction sends 2029.

## Notifications

<InArticleAd />


A read gives the client one value, once. To follow a changing reading it would have to read again and again (polling), like calling a shop every minute to ask whether your order is ready. A notification is leaving your number: the client asks once, and the server then sends each new value by itself. The radio is used only when there is something new, which saves power on both sides.

### How Notifications Work

The switch is the Client Characteristic Configuration Descriptor (CCCD), UUID `0x2902`. NimBLE adds one to every characteristic that has the `NOTIFY` flag. The CCCD is a 16-bit value:

- Bit 0 = 1: notifications are on
- Bit 1 = 1: indications are on (the same as notifications, but the client confirms each one)

The client subscribes by writing to the CCCD. NimBLE handles the write and then reports it to your GAP callback as a `BLE_GAP_EVENT_SUBSCRIBE` event. A subscription lasts only as long as the connection. After a disconnect the client must subscribe again.

### Tracking Subscriptions

The firmware must remember whether the connected client has subscribed, and to which value:

```c
static uint16_t conn_handle_active = BLE_HS_CONN_HANDLE_NONE;  /* 0 is a valid handle */
static bool temp_notify_enabled = false;
static bool humi_notify_enabled = false;

static int gap_event_handler(struct ble_gap_event *event, void *arg)
{
    switch (event->type) {
    case BLE_GAP_EVENT_CONNECT:
        if (event->connect.status == 0) {
            ESP_LOGI(TAG, "Connected, handle=%d", event->connect.conn_handle);
            conn_handle_active = event->connect.conn_handle;
        } else {
            ESP_LOGW(TAG, "Connection failed, status=%d", event->connect.status);
            start_advertising();
        }
        break;

    case BLE_GAP_EVENT_DISCONNECT:
        ESP_LOGI(TAG, "Disconnected, reason=%d",
                 event->disconnect.reason);
        conn_handle_active = BLE_HS_CONN_HANDLE_NONE;
        temp_notify_enabled = false;
        humi_notify_enabled = false;
        start_advertising();  /* Resume advertising */
        break;

    case BLE_GAP_EVENT_SUBSCRIBE:
        ESP_LOGI(TAG, "Subscribe event: attr_handle=%d, cur_notify=%d",
                 event->subscribe.attr_handle,
                 event->subscribe.cur_notify);

        if (event->subscribe.attr_handle == temp_chr_val_handle) {
            temp_notify_enabled = event->subscribe.cur_notify;
            ESP_LOGI(TAG, "Temperature notifications %s",
                     temp_notify_enabled ? "enabled" : "disabled");
        }
        if (event->subscribe.attr_handle == humi_chr_val_handle) {
            humi_notify_enabled = event->subscribe.cur_notify;
            ESP_LOGI(TAG, "Humidity notifications %s",
                     humi_notify_enabled ? "enabled" : "disabled");
        }
        break;

    case BLE_GAP_EVENT_ADV_COMPLETE:
        ESP_LOGI(TAG, "Advertising complete");
        start_advertising();
        break;

    case BLE_GAP_EVENT_MTU:
        ESP_LOGI(TAG, "MTU updated: %d", event->mtu.value);
        break;

    default:
        break;
    }

    return 0;
}
```

### Sending Notifications

To push a value update, use `ble_gatts_notify_custom()`. This builds a notification packet and sends it to the connected client:

```c
static void send_notification(uint16_t attr_handle, void *data, uint16_t len)
{
    if (conn_handle_active == BLE_HS_CONN_HANDLE_NONE) {
        return;  /* No connection */
    }

    struct os_mbuf *om = ble_hs_mbuf_from_flat(data, len);
    if (om == NULL) {
        ESP_LOGE(TAG, "Failed to allocate mbuf for notification");
        return;
    }

    int rc = ble_gatts_notify_custom(conn_handle_active, attr_handle, om);
    if (rc != 0) {
        ESP_LOGE(TAG, "Notification failed, rc=%d", rc);
    }
}
```

The sensor task calls this function whenever a new reading is available:

```c
/* In the sensor reading task */
if (temp_notify_enabled) {
    send_notification(temp_chr_val_handle,
                      &current_temp_ble, sizeof(current_temp_ble));
}
if (humi_notify_enabled) {
    send_notification(humi_chr_val_handle,
                      &current_humi_ble, sizeof(current_humi_ble));
}
```

## Connection Management

<InArticleAd />


Two connected devices do not keep their radios on: they meet on the radio at fixed moments and sleep between them. Three numbers, the connection parameters, set this timetable, and so how fast data moves and how much power the link uses.

### Connection Parameters

| Parameter | Description | Our Value |
|-----------|-------------|-----------|
| Connection Interval | The time between two meetings of central and peripheral | 7.5 ms min, 30 ms max |
| Slave Latency (peripheral latency in newer documents) | How many meetings the peripheral may miss when it has nothing to send | 0 (attend every meeting) |
| Supervision Timeout | How long with no answer before the link counts as lost | 4000 ms |

The central decides, but the peripheral may ask for the values that suit it. The code writes them in the units of the standard: 1.25 ms for the interval and 10 ms for the timeout.

```c
case BLE_GAP_EVENT_CONNECT:
    if (event->connect.status == 0) {
        conn_handle_active = event->connect.conn_handle;

        /* Request connection parameter update */
        struct ble_gap_upd_params params = {
            .itvl_min = 6,    /* 7.5 ms (units of 1.25 ms) */
            .itvl_max = 24,   /* 30 ms (units of 1.25 ms) */
            .latency  = 0,
            .supervision_timeout = 400,  /* 4000 ms (units of 10 ms) */
            .min_ce_len = 0,
            .max_ce_len = 0,
        };
        ble_gap_update_params(conn_handle_active, &params);
    }
    break;
```

### Bonding Basics

Pairing is the step in which two devices agree on keys to encrypt the link; bonding stores the keys, so the next connection does not pair again. Our sensor does not use it: any phone in range can connect and read the values, acceptable for room temperature and not for private data. NimBLE supports bonding through its Security Manager (`ble_hs_cfg.sm_bonding = 1`) and stores the keys in NVS, the small key-value store in flash.

## BLE and Wi-Fi Coexistence

<InArticleAd />


The ESP32 has one 2.4 GHz radio, shared by Wi-Fi and Bluetooth. It cannot serve both at the same moment, so the two take turns many times a second: coexistence (coex). A part of the chip, the arbiter, gives the radio to whichever need is more urgent at that moment. The cost: each protocol is a little slower and less regular than alone.

### How Coexistence Works

When BLE and Wi-Fi are both active, the arbiter works in outline like this (the exact rules are inside Espressif's closed radio library):

1. Wi-Fi beacons and BLE advertising come first, because a link that misses them is lost.
2. Wi-Fi data comes first while a TCP transfer is running.
3. The BLE connection meetings are placed in the gaps between Wi-Fi transmissions.
4. When two needs collide, the less urgent one is delayed or skipped.

### Enabling Coexistence

Coexistence is enabled in menuconfig:

```
Component config > Wireless Coexistence > Software controls WiFi/Bluetooth coexistence > Enable
```

You can also set the coexistence mode to favor one protocol:

| Mode | Behavior |
|------|----------|
| `ESP_COEX_PREFER_WIFI` | Wi-Fi gets priority. BLE may experience higher latency |
| `ESP_COEX_PREFER_BT` | BLE gets priority. Wi-Fi throughput may drop |
| `ESP_COEX_PREFER_BALANCE` | Balanced approach for mixed workloads |

In code, set the preference with:

```c
#include "esp_coexist.h"

esp_coex_preference_set(ESP_COEX_PREFER_BALANCE);
```

In ESP-IDF 5.x this function is marked deprecated (it still builds, with a warning), and balance is already the default, so most projects leave the call out.

### Practical Tips for Coexistence

1. Use a longer BLE connection interval while Wi-Fi is active. An interval of 30 ms leaves Wi-Fi more of the time than 7.5 ms does.
2. Prefer notifications to reads. The peripheral chooses when a notification goes, so the stack can place it around Wi-Fi activity. A read arrives when the client decides.
3. If BLE packets are lost when Wi-Fi is busy, send less over Wi-Fi at one time.

#include <stdio.h>
#include <string.h>
#include <stdlib.h>

#include "host/ble_hs.h"
#include "host/util/util.h"
#include "services/gap/ble_svc_gap.h"
#include "services/gatt/ble_svc_gatt.h"

static const char *TAG = "BLE_ENV";

/* ------------------------------------------------------------------ */
/* DHT22 Configuration                                                */
/* ------------------------------------------------------------------ */
#define DHT22_GPIO       GPIO_NUM_4
#define SENSOR_READ_INTERVAL_MS  5000

/* ------------------------------------------------------------------ */
/* BLE State                                                          */
/* ------------------------------------------------------------------ */
static const char *device_name = "ESP32-ENV";
static uint16_t conn_handle_active = BLE_HS_CONN_HANDLE_NONE;
static bool is_connected = false;
static bool temp_notify_enabled = false;
static bool humi_notify_enabled = false;

static uint16_t temp_chr_val_handle;
static uint16_t humi_chr_val_handle;

/* Sensor values in BLE format */
/* Until the first good reading: the standard "value is not known" */
static int16_t  current_temp_ble = INT16_MIN;   /* 0.01 C units, 0x8000 */
static uint16_t current_humi_ble = 0xFFFF;      /* 0.01 % units */

/* ------------------------------------------------------------------ */
/* DHT22 Bit-Bang Driver                                              */
/* ------------------------------------------------------------------ */
static bool dht22_read(float *temperature, float *humidity)
{
    uint8_t data[5] = {0};
    int64_t timeout;

    /* Send start signal: pull low 2 ms, then release.
     * A busy-wait is used because vTaskDelay(pdMS_TO_TICKS(2)) is
     * zero ticks at the default 100 Hz tick rate. */
    gpio_set_direction(DHT22_GPIO, GPIO_MODE_OUTPUT);
    gpio_set_level(DHT22_GPIO, 0);
    esp_rom_delay_us(2000);
    gpio_set_level(DHT22_GPIO, 1);

    /* Switch to input and wait for sensor response */
    gpio_set_direction(DHT22_GPIO, GPIO_MODE_INPUT);

    /* Wait for sensor to pull low (response signal) */
    timeout = esp_timer_get_time() + 100;
    while (gpio_get_level(DHT22_GPIO) == 1) {
        if (esp_timer_get_time() > timeout) return false;
    }

    /* Sensor holds low ~80 us, then high ~80 us */
    timeout = esp_timer_get_time() + 100;
    while (gpio_get_level(DHT22_GPIO) == 0) {
        if (esp_timer_get_time() > timeout) return false;
    }
    timeout = esp_timer_get_time() + 100;
    while (gpio_get_level(DHT22_GPIO) == 1) {
        if (esp_timer_get_time() > timeout) return false;
    }

    /* Read 40 bits (5 bytes) */
    for (int i = 0; i < 40; i++) {
        /* Wait for bit start (low ~50 us) */
        timeout = esp_timer_get_time() + 100;
        while (gpio_get_level(DHT22_GPIO) == 0) {
            if (esp_timer_get_time() > timeout) return false;
        }
        /* Measure high duration: ~26 us = 0, ~70 us = 1 */
        int64_t start = esp_timer_get_time();
        timeout = start + 100;
        while (gpio_get_level(DHT22_GPIO) == 1) {
            if (esp_timer_get_time() > timeout) return false;
        }
        int64_t duration = esp_timer_get_time() - start;

        data[i / 8] <<= 1;
        if (duration > 40) {
            data[i / 8] |= 1;
        }
    }

    /* Verify checksum */
    uint8_t checksum = data[0] + data[1] + data[2] + data[3];
    if (checksum != data[4]) {
        ESP_LOGW(TAG, "DHT22 checksum mismatch");
        return false;
    }

    /* Parse humidity (unsigned) */
    uint16_t raw_humi = (data[0] << 8) | data[1];
    *humidity = raw_humi * 0.1f;

    /* Parse temperature (signed: bit 15 = sign) */
    uint16_t raw_temp = (data[2] << 8) | data[3];
    if (raw_temp & 0x8000) {
        raw_temp &= 0x7FFF;
        *temperature = raw_temp * -0.1f;
    } else {
        *temperature = raw_temp * 0.1f;
    }

    return true;
}

/* ------------------------------------------------------------------ */
/* GATT Access Callback                                               */
/* ------------------------------------------------------------------ */
static int gatt_access_cb(uint16_t conn_handle, uint16_t attr_handle,
                          struct ble_gatt_access_ctxt *ctxt, void *arg)
{
    uint16_t uuid16 = ble_uuid_u16(ctxt->chr->uuid);
    int rc;

    if (ctxt->op == BLE_GATT_ACCESS_OP_READ_CHR) {
        if (uuid16 == 0x2A6E) {
            rc = os_mbuf_append(ctxt->om, &current_temp_ble,
                                sizeof(current_temp_ble));
            ESP_LOGI(TAG, "Temperature read: %d (0.01 C)", current_temp_ble);
            return rc == 0 ? 0 : BLE_ATT_ERR_INSUFFICIENT_RES;
        }
        if (uuid16 == 0x2A6F) {
            rc = os_mbuf_append(ctxt->om, &current_humi_ble,
                                sizeof(current_humi_ble));
            ESP_LOGI(TAG, "Humidity read: %d (0.01%%)", current_humi_ble);
            return rc == 0 ? 0 : BLE_ATT_ERR_INSUFFICIENT_RES;
        }
    }

    return BLE_ATT_ERR_UNLIKELY;
}

/* ------------------------------------------------------------------ */
/* GATT Service Definitions                                           */
/* ------------------------------------------------------------------ */
static const struct ble_gatt_svc_def gatt_svr_svcs[] = {
    {
        .type = BLE_GATT_SVC_TYPE_PRIMARY,
        .uuid = BLE_UUID16_DECLARE(0x181A),  /* Environmental Sensing */
        .characteristics = (struct ble_gatt_chr_def[]) {
            {
                .uuid = BLE_UUID16_DECLARE(0x2A6E),  /* Temperature */
                .access_cb = gatt_access_cb,
                .val_handle = &temp_chr_val_handle,
                .flags = BLE_GATT_CHR_F_READ | BLE_GATT_CHR_F_NOTIFY,
            },
            {
                .uuid = BLE_UUID16_DECLARE(0x2A6F),  /* Humidity */
                .access_cb = gatt_access_cb,
                .val_handle = &humi_chr_val_handle,
                .flags = BLE_GATT_CHR_F_READ | BLE_GATT_CHR_F_NOTIFY,
            },
            { 0 },
        },
    },
    { 0 },
};

static int gatt_svr_init(void)
{
    int rc;

    ble_svc_gap_init();
    ble_svc_gatt_init();

    rc = ble_gatts_count_cfg(gatt_svr_svcs);
    if (rc != 0) {
        ESP_LOGE(TAG, "ble_gatts_count_cfg failed, rc=%d", rc);
        return rc;
    }

    rc = ble_gatts_add_svcs(gatt_svr_svcs);
    if (rc != 0) {
        ESP_LOGE(TAG, "ble_gatts_add_svcs failed, rc=%d", rc);
        return rc;
    }

    return 0;
}

/* ------------------------------------------------------------------ */
/* Notification Helper                                                */
/* ------------------------------------------------------------------ */
static void send_notification(uint16_t attr_handle, void *data, uint16_t len)
{
    if (!is_connected) {
        return;
    }

    struct os_mbuf *om = ble_hs_mbuf_from_flat(data, len);
    if (om == NULL) {
        ESP_LOGE(TAG, "Failed to allocate mbuf for notification");
        return;
    }

    int rc = ble_gatts_notify_custom(conn_handle_active, attr_handle, om);
    if (rc != 0) {
        ESP_LOGW(TAG, "Notification failed, rc=%d", rc);
    }
}

/* Forward declarations (start_advertising and gap_event_handler reference each other) */
static int gap_event_handler(struct ble_gap_event *event, void *arg);
static void start_advertising(void);

/* ------------------------------------------------------------------ */
/* Advertising                                                        */
/* ------------------------------------------------------------------ */
static void start_advertising(void)
{
    struct ble_gap_adv_params adv_params;
    struct ble_hs_adv_fields fields;
    int rc;

    memset(&fields, 0, sizeof(fields));

    fields.flags = BLE_HS_ADV_F_DISC_GEN | BLE_HS_ADV_F_BREDR_UNSUP;
    fields.name = (uint8_t *)device_name;
    fields.name_len = strlen(device_name);
    fields.name_is_complete = 1;

    ble_uuid16_t ess_uuid = BLE_UUID16_INIT(0x181A);
    fields.uuids16 = &ess_uuid;
    fields.num_uuids16 = 1;
    fields.uuids16_is_complete = 1;

    rc = ble_gap_adv_set_fields(&fields);
    if (rc != 0) {
        ESP_LOGE(TAG, "ble_gap_adv_set_fields failed, rc=%d", rc);
        return;
    }

    memset(&adv_params, 0, sizeof(adv_params));
    adv_params.conn_mode = BLE_GAP_CONN_MODE_UND;
    adv_params.disc_mode = BLE_GAP_DISC_MODE_GEN;
    adv_params.itvl_min = BLE_GAP_ADV_ITVL_MS(100);  /* 100 ms */
    adv_params.itvl_max = BLE_GAP_ADV_ITVL_MS(150);  /* 150 ms */

    rc = ble_gap_adv_start(BLE_OWN_ADDR_PUBLIC, NULL, BLE_HS_FOREVER,
                           &adv_params, gap_event_handler, NULL);
    if (rc != 0 && rc != BLE_HS_EALREADY) {
        ESP_LOGE(TAG, "ble_gap_adv_start failed, rc=%d", rc);
    } else {
        ESP_LOGI(TAG, "Advertising started");
    }
}

/* ------------------------------------------------------------------ */
/* GAP Event Handler                                                  */
/* ------------------------------------------------------------------ */
static int gap_event_handler(struct ble_gap_event *event, void *arg)
{
    switch (event->type) {
    case BLE_GAP_EVENT_CONNECT:
        if (event->connect.status == 0) {
            ESP_LOGI(TAG, "Connection established, handle=%d",
                     event->connect.conn_handle);
            conn_handle_active = event->connect.conn_handle;
            is_connected = true;

            /* Request preferred connection parameters */
            struct ble_gap_upd_params params = {
                .itvl_min = 6,     /* 7.5 ms */
                .itvl_max = 24,    /* 30 ms */
                .latency  = 0,
                .supervision_timeout = 400,  /* 4 seconds */
                .min_ce_len = 0,
                .max_ce_len = 0,
            };
            ble_gap_update_params(conn_handle_active, &params);
        } else {
            ESP_LOGW(TAG, "Connection failed, status=%d",
                     event->connect.status);
            is_connected = false;
            start_advertising();
        }
        break;

    case BLE_GAP_EVENT_DISCONNECT:
        ESP_LOGI(TAG, "Disconnected, reason=0x%02x",
                 event->disconnect.reason);
        conn_handle_active = BLE_HS_CONN_HANDLE_NONE;
        is_connected = false;
        temp_notify_enabled = false;
        humi_notify_enabled = false;
        start_advertising();
        break;

    case BLE_GAP_EVENT_SUBSCRIBE:
        ESP_LOGI(TAG, "Subscribe: handle=%d, notify=%d, indicate=%d",
                 event->subscribe.attr_handle,
                 event->subscribe.cur_notify,
                 event->subscribe.cur_indicate);

        if (event->subscribe.attr_handle == temp_chr_val_handle) {
            temp_notify_enabled = event->subscribe.cur_notify;
        }
        if (event->subscribe.attr_handle == humi_chr_val_handle) {
            humi_notify_enabled = event->subscribe.cur_notify;
        }
        break;

    case BLE_GAP_EVENT_ADV_COMPLETE:
        start_advertising();
        break;

    case BLE_GAP_EVENT_MTU:
        ESP_LOGI(TAG, "MTU update: conn_handle=%d, mtu=%d",
                 event->mtu.conn_handle, event->mtu.value);
        break;

    case BLE_GAP_EVENT_CONN_UPDATE:
        ESP_LOGI(TAG, "Connection parameters updated");
        break;

    default:
        break;
    }

    return 0;
}

/* ------------------------------------------------------------------ */
/* BLE Host Task and Sync Callback                                    */
/* ------------------------------------------------------------------ */
static void ble_on_sync(void)
{
    int rc;

    /* Use the default public address */
    rc = ble_hs_util_ensure_addr(0);
    if (rc != 0) {
        ESP_LOGE(TAG, "Failed to ensure address, rc=%d", rc);
        return;
    }

    start_advertising();
}

static void ble_on_reset(int reason)
{
    ESP_LOGE(TAG, "BLE host reset, reason=%d", reason);
}

static void ble_host_task(void *param)
{
    ESP_LOGI(TAG, "NimBLE host task started");
    nimble_port_run();
    nimble_port_freertos_deinit();
}

/* ------------------------------------------------------------------ */
/* Sensor Reading Task                                                */
/* ------------------------------------------------------------------ */
static void sensor_task(void *param)
{
    float temperature, humidity;

    /* Configure DHT22 GPIO */
    gpio_reset_pin(DHT22_GPIO);
    gpio_set_pull_mode(DHT22_GPIO, GPIO_PULLUP_ONLY);

    /* Wait for initial sensor warm-up */
    vTaskDelay(pdMS_TO_TICKS(2000));

    while (1) {
        if (dht22_read(&temperature, &humidity)) {
            /* Convert to BLE format */
            current_temp_ble = (int16_t)lroundf(temperature * 100.0f);
            current_humi_ble = (uint16_t)lroundf(humidity * 100.0f);

            ESP_LOGI(TAG, "Sensor: %.1f C, %.1f%% RH | BLE: temp=%d, humi=%d",
                     temperature, humidity,
                     current_temp_ble, current_humi_ble);

            /* Send notifications if subscribed */
            if (temp_notify_enabled) {
                send_notification(temp_chr_val_handle,
                                  &current_temp_ble, sizeof(current_temp_ble));
            }
            if (humi_notify_enabled) {
                send_notification(humi_chr_val_handle,
                                  &current_humi_ble, sizeof(current_humi_ble));
            }
        } else {
            ESP_LOGW(TAG, "DHT22 read failed");
        }

        vTaskDelay(pdMS_TO_TICKS(SENSOR_READ_INTERVAL_MS));
    }
}

/* ------------------------------------------------------------------ */
/* Application Entry Point                                            */
/* ------------------------------------------------------------------ */
void app_main(void)
{
    int rc;

    ESP_LOGI(TAG, "BLE Environmental Sensor starting");

    /* Initialize NVS (required for BLE bonding storage) */
    esp_err_t ret = nvs_flash_init();
    if (ret == ESP_ERR_NVS_NO_FREE_PAGES ||
        ret == ESP_ERR_NVS_NEW_VERSION_FOUND) {
        ESP_ERROR_CHECK(nvs_flash_erase());
        ret = nvs_flash_init();
    }
    ESP_ERROR_CHECK(ret);

    /* Initialize the NimBLE host */
    ret = nimble_port_init();
    if (ret != ESP_OK) {
        ESP_LOGE(TAG, "nimble_port_init failed, ret=%d", ret);
        return;
    }

    /* Configure the NimBLE host */
    ble_hs_cfg.sync_cb  = ble_on_sync;
    ble_hs_cfg.reset_cb = ble_on_reset;

    /* Set the device name */
    rc = ble_svc_gap_device_name_set(device_name);
    if (rc != 0) {
        ESP_LOGE(TAG, "Failed to set device name, rc=%d", rc);
    }

    /* Initialize the GATT server */
    rc = gatt_svr_init();
    if (rc != 0) {
        ESP_LOGE(TAG, "GATT server init failed, rc=%d", rc);
        return;
    }

    /* Start the NimBLE host task */
    nimble_port_freertos_init(ble_host_task);

    /* Start the sensor reading task */
    xTaskCreate(sensor_task, "sensor_task", 4096, NULL, 5, NULL);

    ESP_LOGI(TAG, "Initialization complete");
}

## Testing with a Phone App

<InArticleAd />


Test the sensor with nRF Connect, a free app for Android and iOS.

<Steps>
1. Install **nRF Connect** from the Google Play Store or Apple App Store.

2. Open the app and tap **Scan**. The device appears as **ESP32-ENV**.

3. Tap **Connect**. The app connects and shows the GATT services.

4. Open the **Environmental Sensing** service (UUID 0x181A). It has two characteristics: **Temperature** (0x2A6E) and **Humidity** (0x2A6F).

5. Tap the **single down-arrow icon** beside Temperature to read it once. The app shows the raw bytes and, because it knows the standard UUID, perhaps the value too ("24.30 C").

6. Tap the **triple down-arrow icon** beside Temperature to switch notifications on. The value now changes every 5 seconds.

7. Do the same for Humidity.

8. Look at the serial monitor of the ESP32. The log shows the connection and the subscription.
</Steps>

### Check it

The phone shows a number; check that it is the number the sensor measured.

1. **The bytes.** Read Temperature once in nRF Connect and compare the raw bytes with the serial log. A log line `temp=2430` must appear as `7E 09` (0x097E = 2430, low byte first). Bytes in the other order (`09 7E`) mean the value was sent high byte first, and a phone app that follows the standard would show 322.65 °C (it reads 0x7E09 = 32265).
2. **The rate.** With notifications on, count the updates for one minute: at one reading every 5 seconds you should see 12. A reading that fails its checksum sends nothing, so 10 or 11 is normal; far fewer means the DHT22 fails often.
3. **The range.** Walk away with the phone and watch the RSSI that nRF Connect shows for the device. Note the distance at which notifications stop. Indoors, through walls, it is often well under the 10 m of the table: measure it where the sensor will be used.

### Troubleshooting

| Problem | Possible Cause | Solution |
|---------|----------------|----------|
| Device not found in scan | Advertising not started | Check serial output for "Advertising started" message |
| Connection drops immediately | Parameter negotiation failure | Try removing the `ble_gap_update_params` call |
| Read returns `00 80` (temperature) or `FF FF` (humidity) | No good reading yet: the standard "value is not known" | Wait for the first DHT22 reading (2 second warm-up). If it stays, check the DHT22 wiring |
| Notifications not received | CCCD not written | Tap the notification icon in nRF Connect (not just the read icon) |
| "GATT Error 0x0E" | The access callback returned `BLE_ATT_ERR_UNLIKELY` (0x0E) | Check the UUID and operation handled in `gatt_access_cb`. The default MTU (23 bytes, 20 of them for the value) is already enough for 2-byte values |

:::tip[Instrument it]
BLE suits a sensor that must run for months on a small battery and needs to reach only a phone or a gateway nearby: a temperature tag on a cold store door, a vibration tag on a motor. Send the reading as a notification, so that the radio sleeps between updates. A gateway can collect several tags and [forward them onward](/education/iot-systems/) to [a broker you run](/education/iot-systems/mqtt-broker-setup-secure-connection/).
:::

## Summary

<InArticleAd />


You built a BLE sensor with the NimBLE stack that any phone can find and read.

- GAP is how the device is found: an advertising packet of at most 31 bytes, repeated at an interval you choose.
- GATT is how the data is arranged: a service holds characteristics, and each has a UUID. With the standard UUIDs (0x181A, 0x2A6E, 0x2A6F) and the standard formats, any client understands the data.
- Your code does not wait for the radio. NimBLE calls your callbacks when a client connects, reads or subscribes.
- A read gives one value. To follow a value, the client subscribes once by writing to the CCCD, and the server then sends each new reading. The subscription ends with the connection.
- BLE and Wi-Fi share one radio. When both run, use a longer BLE connection interval.
