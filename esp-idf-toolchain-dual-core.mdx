A lamp fades through its colors, and each time you type a command the fade stops for a moment. The cause is a chip with one processor core: while it waits for your keys, it cannot draw the next color. The ESP32 has two cores and a small operating system, FreeRTOS, that gives each core its own work, so one core animates while the other listens. In this lesson you install ESP-IDF, the official programming tools for the ESP32, learn what its settings menu and its flash memory map do, and build an RGB mood lamp that runs the animation on one core and the command reader on the other. #ESP32 #ESPIDF #DualCore

## What You Will Learn

The ESP32 is a small, inexpensive chip with two processor cores, Wi-Fi and Bluetooth. A simpler microcontroller does one thing at a time; the ESP32 can run two tasks at once, one on each core.

You set up its programming tools (ESP-IDF) and build an RGB mood lamp. One core animates the LED while the other listens for your typed commands ("red", "rainbow", "pulse"). Neither core waits for the other, so the animation never stutters and every command is heard at once.

```text
 How the mood lamp works:

 ┌──────────────┐         ┌──────────────┐
 │   Core 0     │         │   Core 1     │
 │              │  queue  │              │
 │ Listens for  ├────────>│ Runs color   │
 │ your typed   │"rainbow"│ animation    │
 │ commands     │         │ on RGB LED   │
 └──────────────┘         └──────────────┘
```

## Installing ESP-IDF

<InArticleAd />


ESP-IDF is three things: a compiler for the ESP32's Xtensa processor, the libraries for the chip's hardware, and one command, `idf.py`, that builds and loads your program. Each new terminal must run the export script so that it can find these tools.

<Tabs>
<TabItem label="Linux (Ubuntu/Debian)">
```bash
# Install prerequisites
sudo apt update
sudo apt install git wget flex bison gperf python3 python3-pip \
    python3-venv cmake ninja-build ccache libffi-dev libssl-dev \
    dfu-util libusb-1.0-0

# Clone ESP-IDF v5.x
mkdir -p ~/esp
cd ~/esp
git clone -b v5.4 --recursive https://github.com/espressif/esp-idf.git

# Run the install script (downloads the Xtensa toolchain)
cd ~/esp/esp-idf
./install.sh esp32

# Source the export script (do this in every new terminal)
. ~/esp/esp-idf/export.sh

# Verify
idf.py --version
```

### USB Serial Driver

Your computer talks to the board through a small USB-to-serial chip on it, most often a CP2102 or a CH340. On Linux, add your user to the `dialout` group, or every flash command fails with "permission denied":

```bash
sudo usermod -aG dialout $USER
# Log out and back in for the group change to take effect
```

On macOS and Windows, install the appropriate driver from the chip manufacturer if the board does not appear as a serial port.

## ESP-IDF Project Structure

<InArticleAd />


An ESP-IDF project is a set of components. A component is a folder of source code with its own small build file, `CMakeLists.txt`. The build system finds each component by its build file and joins them into one program, so you never list library paths by hand.

<FileTree>
- rgb-mood-lamp/
  - CMakeLists.txt
  - main/
    - CMakeLists.txt
    - main.c
  - sdkconfig
  - sdkconfig.defaults
  - build/
</FileTree>

The top-level `CMakeLists.txt` is minimal. It points to the ESP-IDF framework and declares the project name:

```cmake
# Top-level CMakeLists.txt
cmake_minimum_required(VERSION 3.16)
include($ENV{IDF_PATH}/tools/cmake/project.cmake)
project(rgb-mood-lamp)
```

The `main/CMakeLists.txt` registers source files for the main component:

```cmake
# main/CMakeLists.txt
idf_component_register(SRCS "main.c"
                       INCLUDE_DIRS ".")
```

The `main` component is special: it is always included, and it holds `app_main()`, the function where your program starts. You add more components as folders under `components/` at the project root.

## Menuconfig

<InArticleAd />


ESP-IDF has hundreds of settings: the flash size, the processor speed, which drivers to include. All of them sit in one menu, and your choices are saved in one file, `sdkconfig`. They are fixed when you build.

```bash
idf.py menuconfig
```

This opens a menu in the terminal. The settings you meet first:

| Menu Path | Setting | Typical Value |
|-----------|---------|---------------|
| Serial flasher config | Flash size | 4 MB |
| Component config > ESP System Settings | CPU frequency | 240 MHz |
| Partition Table | Partition Table | Single factory app (no OTA) |
| Component config > FreeRTOS | Tick rate (Hz) | 1000 (the default is 100) |
| Component config > ESP System Settings | Main task stack size | 3584 |

The tick rate is how often FreeRTOS decides which task runs next. The stack size is the working memory of one task, in bytes.

The tick rate also sets the shortest delay. `pdMS_TO_TICKS(ms)` turns milliseconds into whole ticks and rounds down. At the default 100 Hz one tick is 10 ms, so a 15 ms delay becomes 10 ms and a 5 ms delay becomes 0 (no wait at all). The lamp uses delays of 10 and 20 ms, which work at either rate; the exercises use 5 and 15 ms, which need 1000 Hz. Put the line `CONFIG_FREERTOS_HZ=1000` in `sdkconfig.defaults` (below) so that every copy of the project builds with it.

Menuconfig writes `sdkconfig` for you, so do not edit that file by hand. To keep a setting in version control, write it in `sdkconfig.defaults`. The build reads `sdkconfig.defaults` first and then applies any existing `sdkconfig` over it.

The two files matter in a team. `sdkconfig` belongs to one machine and goes in `.gitignore`. `sdkconfig.defaults` goes into version control and holds only the settings you chose to change. When a teammate clones the repository, ESP-IDF makes a new `sdkconfig` from the defaults. The [HTTP Server lesson](/education/embedded-programming-esp32/http-server-rest-api/) shows how to add menu entries for your own application settings.

## Partition Table

<InArticleAd />


The flash chip is one long strip of memory shared, without overlap, by the bootloader (the small program that runs first and starts yours), your program and saved data. The partition table is the map. It sits at address 0x8000 and gives each region a name, a start address and a size.

Two regions appear in every project. NVS (non-volatile storage) holds small saved values, such as a Wi-Fi password, that must remain when power is removed. The factory app is your program.

```text
 ┌──────────────────────────────┐ 0x001000
 │  Bootloader (2nd stage)      │
 ├──────────────────────────────┤ 0x008000
 │  Partition Table             │
 ├──────────────────────────────┤ 0x009000
 │  NVS (Non-Volatile Storage)  │ 24 KB
 ├──────────────────────────────┤ 0x00F000
 │  PHY Init Data               │ 4 KB
 ├──────────────────────────────┤ 0x010000
 │                              │
 │  Factory App                 │ 1 MB
 │                              │
 ├──────────────────────────────┤
 │  (Free / custom partitions)  │
 └──────────────────────────────┘ 0x400000
```

This is the default table, named "Single factory app, no OTA". OTA means over the air: a firmware update sent through the network. Note that the program gets 1 MB, not the full 4 MB of the chip. A program larger than its partition does not build, however much flash is free after it.

For a project that needs OTA updates or a file system, you write your own `partitions.csv`:

```csv
# Name,   Type, SubType, Offset,  Size, Flags
nvs,      data, nvs,     0x9000,  0x6000,
phy_init, data, phy,     0xf000,  0x1000,
factory,  app,  factory, 0x10000, 1M,
storage,  data, spiffs,  ,        512K,
```

Then select "Custom partition table CSV" in menuconfig and point it to your file. View the compiled partition table at any time:

```bash
idf.py partition-table
```

This prints the table with its addresses and sizes, so you can check that no two partitions overlap. You write a custom table again for [OTA updates](/education/embedded-programming-esp32/ota-updates-secure-boot/), where the flash holds two copies of the program so that a failed update can fall back to the old one.

## Dual-Core Architecture

<InArticleAd />


The ESP32 contains two processor cores of the Xtensa LX6 type, each running at up to 240 MHz. Espressif names them PRO_CPU (core 0) and APP_CPU (core 1).

In FreeRTOS your program is a set of tasks. A task is a function with its own loop and its own stack, and the scheduler decides which task runs at each moment. Think of two cooks (the cores) who take orders (the tasks) from one board. Either cook takes any order, unless it carries a cook's name. That is symmetric multiprocessing (SMP): one FreeRTOS, one memory, two cores, and a task runs on either core unless you pin it to one. Where the picture stops being true: a pinned task waits for its own core, even when the other core has nothing to do.

```text
 ┌───────────────┐       ┌───────────────┐
 │ PRO_CPU       │       │ APP_CPU       │
 │ core 0        │       │ core 1        │
 └───────┬───────┘       └───────┬───────┘
         │   ┌───────────────┐   │
         └───┤ one FreeRTOS, ├───┘
             │ one task list │
             └───────┬───────┘
 ┌───────────────────┴───────────────────┐
 │ shared: 520 KB RAM, GPIO, timers, ... │
 └───────────────────────────────────────┘
```

Both cores see the same memory, so two tasks can write one variable at the same moment. This is why the lamp passes its commands through a queue.

### How Boot and System Tasks Are Distributed

At startup ESP-IDF also creates tasks of its own, most of them on core 0:

| Task | Core | Purpose |
|------|------|---------|
| main (app_main) | PRO_CPU (0) | Your application entry point |
| IDLE0 | PRO_CPU (0) | Idle task for core 0 |
| IDLE1 | APP_CPU (1) | Idle task for core 1 |
| esp_timer | PRO_CPU (0) | Software timer callbacks |
| Wi-Fi task | PRO_CPU (0) | Wi-Fi protocol stack |
| ipc0, ipc1 | 0, 1 | Inter-processor call tasks |

An idle task runs when its core has nothing else to do. The `app_main()` function is itself a task on core 0, with a default stack of 3584 bytes. From it you create your own tasks.

### Task Creation and Core Pinning

The standard FreeRTOS `xTaskCreate()` lets the scheduler put the task on either core. To pin a task, use the ESP-IDF version, which takes the core number as its last argument:

```c
#include "freertos/FreeRTOS.h"
#include "freertos/task.h"

void my_task(void *pvParameters) {
    while (1) {
        /* This task runs only on core 1 */
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void app_main(void) {
    xTaskCreatePinnedToCore(
        my_task,          /* Task function */
        "my_task",        /* Name (for debugging) */
        4096,             /* Stack size in bytes */
        NULL,             /* Parameter */
        5,                /* Priority (higher = more urgent) */
        NULL,             /* Task handle (optional) */
        1                 /* Core ID: 0 = PRO_CPU, 1 = APP_CPU */
    );
}
```

Pass `tskNO_AFFINITY` as the last argument to let the scheduler choose the core.

### When to Pin Tasks

Pin a task when:

- its timing is strict (motor control, audio sampling), so that it does not wait behind the Wi-Fi and Bluetooth tasks on core 0;
- it uses hardware that only one task may touch at a time.

Leave a task unpinned when a short delay does not matter. The scheduler then runs it on whichever core is free.

Espressif chose SMP over asymmetric multiprocessing (AMP), in which each core runs its own operating system with its own memory. With SMP a shared queue is enough to pass data between tasks, but shared data needs a lock.

One consequence concerns interrupts. An interrupt handler (ISR) runs on the core that registered it, which may not be the core your task is pinned to. An ISR may not wait, so it cannot take a mutex. On a one-core chip you protect data shared with an ISR by turning interrupts off for a moment, but on the ESP32 that stops interrupts only on your own core, and the other core continues. So use a spinlock (`portMUX_TYPE`, with `portENTER_CRITICAL()` in the task and `portENTER_CRITICAL_ISR()` in the ISR), which also holds the other core back. The [RTOS Programming course](/education/rtos-programming/) covers these locks.

In most connected products, core 0 runs the network tasks (Wi-Fi, Bluetooth, MQTT) and core 1 runs the application's control loop, so that a slow network never delays a measurement. The lessons on [Wi-Fi](/education/embedded-programming-esp32/wifi-network-configuration/) and [MQTT](/education/embedded-programming-esp32/mqtt-cloud-communication/) keep the network on core 0, and the [capstone project](/education/embedded-programming-esp32/connected-sensor-network-project/) builds a sensor network on the same split. The [IoT Systems course](/education/iot-systems/) uses it for systems with many sensors.

## LEDC PWM for RGB LED

<InArticleAd />


A GPIO pin is only on or off. With PWM it switches faster than the eye can follow, and the eye sees the average. The fraction of each period that the pin is on is the duty cycle.

LEDC (LED Control) is the ESP32 peripheral that makes PWM in hardware. It has up to 16 channels. A timer sets the frequency and the resolution, and each channel connects one pin to a timer with its own duty. The lamp uses three channels on one timer, so the three colors switch at the same frequency.

With the settings below, the frequency is 5 kHz, so one period is 200 µs. The resolution is 8 bits, so the duty is a number from 0 to 255. A duty of 64 keeps the pin on for 64/256 of the period, which is 50 µs.

### Timer and Channel Configuration

Configure the timer first, then the channels:

```c
#include "driver/ledc.h"

#define LEDC_TIMER       LEDC_TIMER_0
#define LEDC_MODE        LEDC_LOW_SPEED_MODE
#define LEDC_FREQUENCY   5000    /* 5 kHz PWM */
#define LEDC_RESOLUTION  LEDC_TIMER_8_BIT  /* 0-255 duty range */

#define GPIO_RED    25
#define GPIO_GREEN  26
#define GPIO_BLUE   27

void ledc_init(void) {
    /* Configure the timer */
    ledc_timer_config_t timer_conf = {
        .speed_mode      = LEDC_MODE,
        .duty_resolution = LEDC_RESOLUTION,
        .timer_num       = LEDC_TIMER,
        .freq_hz         = LEDC_FREQUENCY,
        .clk_cfg         = LEDC_AUTO_CLK,
    };
    ledc_timer_config(&timer_conf);

    /* Configure three channels: red, green, blue */
    int gpios[3] = {GPIO_RED, GPIO_GREEN, GPIO_BLUE};
    for (int ch = 0; ch < 3; ch++) {
        ledc_channel_config_t ch_conf = {
            .speed_mode = LEDC_MODE,
            .channel    = (ledc_channel_t)ch,  /* LEDC_CHANNEL_0, 1, 2 */
            .timer_sel  = LEDC_TIMER,
            .intr_type  = LEDC_INTR_DISABLE,
            .gpio_num   = gpios[ch],
            .duty       = 0,
            .hpoint     = 0,
        };
        ledc_channel_config(&ch_conf);
    }
}
```

To set a color, write duty values to each channel:

```c
void set_rgb(uint8_t r, uint8_t g, uint8_t b) {
    ledc_set_duty(LEDC_MODE, LEDC_CHANNEL_0, r);
    ledc_update_duty(LEDC_MODE, LEDC_CHANNEL_0);

    ledc_set_duty(LEDC_MODE, LEDC_CHANNEL_1, g);
    ledc_update_duty(LEDC_MODE, LEDC_CHANNEL_1);

    ledc_set_duty(LEDC_MODE, LEDC_CHANNEL_2, b);
    ledc_update_duty(LEDC_MODE, LEDC_CHANNEL_2);
}
```

Each color needs two calls. `ledc_set_duty()` only stores the new value in a waiting register. `ledc_update_duty()` makes it active at the start of the next PWM period, so a period is never cut short and the LED does not flicker.

LEDC can also fade in hardware with `ledc_set_fade_with_time()`, which changes the duty step by step with no work from the CPU. The lamp animates in software because each frame needs a color conversion. For a plain change of brightness, use the hardware fade. The [GPIO and Peripherals lesson](/education/embedded-programming-esp32/gpio-peripherals-driver-framework/) uses it.

## HSV to RGB Conversion

<InArticleAd />


To move smoothly through the rainbow in RGB, you must change three numbers together in the right pattern. HSV (hue, saturation, value) describes the same color in a way that suits animation:

- hue is the position on the color circle in degrees (0 = red, 120 = green, 240 = blue);
- saturation is how strong the color is (0 is white or gray);
- value is the brightness.

A rainbow is then one number, the hue, counting from 0 to 359. The function below converts each HSV color to the three duty values the LED needs.

```c
/* Convert HSV to RGB. h: 0-360, s: 0-255, v: 0-255 */
void hsv_to_rgb(uint16_t h, uint8_t s, uint8_t v,
                uint8_t *r, uint8_t *g, uint8_t *b)
{
    if (s == 0) {
        *r = *g = *b = v;
        return;
    }

    uint8_t region = h / 60;
    uint8_t remainder = (h - (region * 60)) * 255 / 60;

    uint8_t p = (v * (255 - s)) >> 8;
    uint8_t q = (v * (255 - ((s * remainder) >> 8))) >> 8;
    uint8_t t = (v * (255 - ((s * (255 - remainder)) >> 8))) >> 8;

    switch (region) {
        case 0:  *r = v; *g = t; *b = p; break;
        case 1:  *r = q; *g = v; *b = p; break;
        case 2:  *r = p; *g = v; *b = t; break;
        case 3:  *r = p; *g = q; *b = v; break;
        case 4:  *r = t; *g = p; *b = v; break;
        default: *r = v; *g = p; *b = q; break;
    }
}
```

## Complete Firmware

<InArticleAd />


The complete `main.c`: the animation task runs on core 1, the command task on core 0, and they never share a variable. The command task puts each new mode into a FreeRTOS queue (a short waiting line that two tasks can use safely), and the animation task takes it out.

```c
#include <stdio.h>
#include <string.h>
#include <ctype.h>

#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "freertos/queue.h"
#include "driver/ledc.h"
#include "driver/uart.h"
#include "driver/uart_vfs.h"
#include "esp_log.h"

static const char *TAG = "mood_lamp";

/* ---------- Pin and PWM configuration ---------- */

#define GPIO_RED    25
#define GPIO_GREEN  26
#define GPIO_BLUE   27

#define LEDC_TIMER       LEDC_TIMER_0
#define LEDC_MODE        LEDC_LOW_SPEED_MODE
#define LEDC_FREQUENCY   5000
#define LEDC_RESOLUTION  LEDC_TIMER_8_BIT   /* 0-255 */

/* ---------- Animation modes ---------- */

typedef enum {
    MODE_OFF,
    MODE_RED,
    MODE_GREEN,
    MODE_BLUE,
    MODE_RAINBOW,
    MODE_PULSE,
} led_mode_t;

/* Queue for sending mode changes from parser to animation task */
static QueueHandle_t mode_queue;

/* ---------- LEDC helpers ---------- */

static void ledc_init(void)
{
    ledc_timer_config_t timer_conf = {
        .speed_mode      = LEDC_MODE,
        .duty_resolution = LEDC_RESOLUTION,
        .timer_num       = LEDC_TIMER,
        .freq_hz         = LEDC_FREQUENCY,
        .clk_cfg         = LEDC_AUTO_CLK,
    };
    ledc_timer_config(&timer_conf);

    int gpios[3] = {GPIO_RED, GPIO_GREEN, GPIO_BLUE};
    for (int ch = 0; ch < 3; ch++) {
        ledc_channel_config_t ch_conf = {
            .speed_mode = LEDC_MODE,
            .channel    = (ledc_channel_t)ch,
            .timer_sel  = LEDC_TIMER,
            .intr_type  = LEDC_INTR_DISABLE,
            .gpio_num   = gpios[ch],
            .duty       = 0,
            .hpoint     = 0,
        };
        ledc_channel_config(&ch_conf);
    }
}

static void set_rgb(uint8_t r, uint8_t g, uint8_t b)
{
    ledc_set_duty(LEDC_MODE, LEDC_CHANNEL_0, r);
    ledc_update_duty(LEDC_MODE, LEDC_CHANNEL_0);

    ledc_set_duty(LEDC_MODE, LEDC_CHANNEL_1, g);
    ledc_update_duty(LEDC_MODE, LEDC_CHANNEL_1);

    ledc_set_duty(LEDC_MODE, LEDC_CHANNEL_2, b);
    ledc_update_duty(LEDC_MODE, LEDC_CHANNEL_2);
}

/* ---------- HSV to RGB ---------- */

static void hsv_to_rgb(uint16_t h, uint8_t s, uint8_t v,
                        uint8_t *r, uint8_t *g, uint8_t *b)
{
    if (s == 0) {
        *r = *g = *b = v;
        return;
    }

    uint8_t region = h / 60;
    uint8_t remainder = (h - (region * 60)) * 255 / 60;

    uint8_t p = (v * (255 - s)) >> 8;
    uint8_t q = (v * (255 - ((s * remainder) >> 8))) >> 8;
    uint8_t t = (v * (255 - ((s * (255 - remainder)) >> 8))) >> 8;

    switch (region) {
        case 0:  *r = v; *g = t; *b = p; break;
        case 1:  *r = q; *g = v; *b = p; break;
        case 2:  *r = p; *g = v; *b = t; break;
        case 3:  *r = p; *g = q; *b = v; break;
        case 4:  *r = t; *g = p; *b = v; break;
        default: *r = v; *g = p; *b = q; break;
    }
}

/* ---------- Animation task (Core 1) ---------- */

static void animation_task(void *pvParameters)
{
    led_mode_t current_mode = MODE_RAINBOW;
    uint16_t hue = 0;
    uint8_t pulse_brightness = 0;
    int8_t pulse_direction = 1;

    ESP_LOGI(TAG, "Animation task running on core %d", xPortGetCoreID());

    while (1) {
        /* Check for mode changes (non-blocking) */
        led_mode_t new_mode;
        if (xQueueReceive(mode_queue, &new_mode, 0) == pdTRUE) {
            current_mode = new_mode;
            hue = 0;
            pulse_brightness = 0;
            pulse_direction = 1;
            ESP_LOGI(TAG, "Mode changed to %d", current_mode);
        }

        uint8_t r = 0, g = 0, b = 0;

        switch (current_mode) {
            case MODE_OFF:
                set_rgb(0, 0, 0);
                vTaskDelay(pdMS_TO_TICKS(100));
                continue;

            case MODE_RED:
                set_rgb(255, 0, 0);
                vTaskDelay(pdMS_TO_TICKS(100));
                continue;

            case MODE_GREEN:
                set_rgb(0, 255, 0);
                vTaskDelay(pdMS_TO_TICKS(100));
                continue;

            case MODE_BLUE:
                set_rgb(0, 0, 255);
                vTaskDelay(pdMS_TO_TICKS(100));
                continue;

            case MODE_RAINBOW:
                hsv_to_rgb(hue, 255, 200, &r, &g, &b);
                set_rgb(r, g, b);
                hue = (hue + 1) % 360;
                vTaskDelay(pdMS_TO_TICKS(20));  /* ~7.2 seconds per full cycle */
                continue;

            case MODE_PULSE: {
                hsv_to_rgb(hue, 255, pulse_brightness, &r, &g, &b);
                set_rgb(r, g, b);
                int new_val = pulse_brightness + pulse_direction * 2;
                if (new_val >= 255) { new_val = 255; pulse_direction = -1; }
                if (new_val <= 0) {
                    new_val = 0;
                    pulse_direction = 1;
                    hue = (hue + 30) % 360;  /* Shift color each pulse */
                }
                pulse_brightness = (uint8_t)new_val;
                vTaskDelay(pdMS_TO_TICKS(10));
                continue;
            }
        }
    }
}

/* ---------- Command parser task (Core 0) ---------- */

static void str_tolower(char *s)
{
    for (; *s; s++) {
        *s = tolower((unsigned char)*s);
    }
}

static void parser_task(void *pvParameters)
{
    char line[64];

    ESP_LOGI(TAG, "Parser task running on core %d", xPortGetCoreID());
    printf("\nRGB Mood Lamp ready. Commands: red, green, blue, rainbow, pulse, off\n> ");
    fflush(stdout);

    while (1) {
        /* Read a line from stdin (UART0) */
        if (fgets(line, sizeof(line), stdin) != NULL) {
            /* Strip newline */
            line[strcspn(line, "\r\n")] = '\0';
            str_tolower(line);

            led_mode_t mode;
            bool valid = true;

            if (strcmp(line, "red") == 0) {
                mode = MODE_RED;
            } else if (strcmp(line, "green") == 0) {
                mode = MODE_GREEN;
            } else if (strcmp(line, "blue") == 0) {
                mode = MODE_BLUE;
            } else if (strcmp(line, "rainbow") == 0) {
                mode = MODE_RAINBOW;
            } else if (strcmp(line, "pulse") == 0) {
                mode = MODE_PULSE;
            } else if (strcmp(line, "off") == 0) {
                mode = MODE_OFF;
            } else {
                valid = false;
                printf("Unknown command: '%s'\n", line);
                printf("Commands: red, green, blue, rainbow, pulse, off\n");
            }

            if (valid) {
                xQueueSend(mode_queue, &mode, pdMS_TO_TICKS(100));
                printf("OK: %s\n", line);
            }
            printf("> ");
            fflush(stdout);
        }

        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

/* ---------- Entry point ---------- */

void app_main(void)
{
    ESP_LOGI(TAG, "RGB Mood Lamp starting on ESP32");

    /* Initialize LEDC PWM */
    ledc_init();
    set_rgb(0, 0, 0);

    /* Create the mode queue (depth 4, each element is a led_mode_t) */
    mode_queue = xQueueCreate(4, sizeof(led_mode_t));

    /* Make stdin block until a full line arrives. Without the UART
       driver, fgets() returns at once and splits a typed command.
       (Before ESP-IDF v5.3 the second call was named
       esp_vfs_dev_uart_use_driver.) */
    uart_driver_install(UART_NUM_0, 256, 0, 0, NULL, 0);
    uart_vfs_dev_use_driver(UART_NUM_0);

    /* Create the animation task, pinned to core 1 */
    xTaskCreatePinnedToCore(
        animation_task,
        "animation",
        4096,
        NULL,
        5,
        NULL,
        1       /* APP_CPU */
    );

    /* Create the parser task, pinned to core 0 */
    xTaskCreatePinnedToCore(
        parser_task,
        "parser",
        4096,
        NULL,
        5,
        NULL,
        0       /* PRO_CPU */
    );

    /* app_main can return; the tasks keep running */
}
```

### How the Code Works

1. `animation_task` on core 1 checks the queue with a timeout of zero, so it never waits there. It sets a fixed color or computes the next frame, then calls `vTaskDelay()`. The delay sets the animation speed and gives the core to other tasks: a loop with no delay would keep core 1 for itself.

2. `parser_task` on core 0 waits in `fgets()` until a full line arrives. A task that waits uses no processor time. It removes the line ending, converts the text to lower case and compares it with the known commands. A valid command goes into the queue.

3. `app_main()` sets up LEDC, creates the queue, creates both tasks and returns. On a PC, a program ends when `main()` returns. Here `app_main()` is only one task: when it returns, that task is deleted and the two pinned tasks continue.

### Wiring the RGB LED

```text
        ESP32 DevKitC
       ┌─────────────┐
       │         GP25 ├──[R1 220R]──┐
       │         GP26 ├──[R2 220R]──┤── RGB LED
       │         GP27 ├──[R3 220R]──┤   (Common
       │          GND ├─────────────┘   Cathode)
       │              │
       │     USB      │
       └──────┤├──────┘
```

A common-cathode RGB LED is three LEDs in one case that share their negative pin. The longest pin is the common cathode and goes to GND. The red, green and blue pins go to GPIO 25, 26 and 27, each through its own 220 ohm resistor.

The resistor limits the current, which protects the LED and the pin. The pin gives 3.3 V and a red LED keeps about 2.0 V, so 1.3 V is left across 220 ohm: about 6 mA. That is well below the pin's default drive strength of about 20 mA.

The green and blue parts of most RGB LEDs keep about 3.0 V. Only 0.3 V is then left across 220 ohm, about 1.4 mA, so green and blue look much weaker than red and the rainbow looks mostly red. For even colors, use a smaller resistor on green and blue (68 ohm gives about 4 mA at 3.0 V), and read the forward voltage of each color in your LED's datasheet.

### Check it

Before you trust the lamp, check three things:

1. **The cores.** The log must show `Animation task running on core 1` and `Parser task running on core 0`. Any other number means a wrong core ID in `xTaskCreatePinnedToCore()`.
2. **The split.** In `rainbow` mode, time ten full color cycles with a stopwatch: 360 steps of 20 ms give 7.2 s per cycle, so about 72 s. During the count, type an unknown word (for example `x`) a few times. The fade must not pause or slow, because the parser waits on the other core. If it does pause, check that the two tasks are really on different cores.
3. **The current.** With the lamp on `red`, measure the voltage across R1 with a multimeter and divide by 220 ohm. About 1.3 V (6 mA) is right. Near 0 V means the LED is in backwards or is common anode; near 3.3 V means the LED is shorted.

## Exercises

<InArticleAd />


1. **Add a "breathe" mode.** Add `MODE_BREATHE`: hold one color (for example warm white, hue 30) and ramp the HSV value from 0 to 255 and back. A step delay of about 15 ms gives a smooth breath of about 8 seconds.

2. **Add speed control commands.** "fast" halves the animation delay and "slow" doubles it, limited to 5 ms to 100 ms. Keep the delay in a shared variable protected by a mutex, or send it through a second queue.

3. **Print mode and core info on each change.** When the animation task receives a new mode, print the mode name, the core ID (`xPortGetCoreID()`) and the tick count (`xTaskGetTickCount()`). This shows that each task really runs on its pinned core.

4. **Add a "status" command.** On "status", print the free heap (`esp_get_free_heap_size()`), the number of tasks (`uxTaskGetNumberOfTasks()`) and the uptime in seconds (`esp_timer_get_time() / 1000000`). It uses the ESP-IDF system functions and does not touch the animation loop.

## Summary

<InArticleAd />


- ESP-IDF is the compiler, the libraries and `idf.py`. Menuconfig saves the build settings in `sdkconfig`.
- The partition table is the map of the flash. A program must fit its own partition.
- The two cores share one FreeRTOS and one memory. A task runs on either core unless you pin it, and a pinned task waits for its own core.
- Tasks on different cores pass data through a queue, not through a shared variable.
- LEDC makes PWM in hardware: a timer sets the frequency and resolution, and each channel has its own duty.
